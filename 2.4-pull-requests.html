Lektion 2.4 — Teil 2: Branches & Zusammenarbeit

Pull Requests auf GitHub

Pull Requests ca. 90 min Fortgeschritten

Lernziele

  • Andere Personen als Collaborators zu einem Repository einladen
  • Einen Pull Request mit aussagekräftiger Beschreibung erstellen
  • Code Reviews durchführen: kommentieren, Änderungen vorschlagen, zustimmen
  • Die drei Merge-Varianten auf GitHub unterscheiden und passend wählen
  • main mit Branch-Regeln vor direkten Pushes schützen
  • Pull Requests mit Issues verknüpfen und den Fork-Workflow erklären

1 — Zusammenarbeit einrichten

Ein öffentliches Repository kann jeder lesen, aber nur du darfst pushen. Damit dein Team Branches pushen kann, lädst du die Mitglieder als Collaborators ein:

  1. Repository → Settings → Collaborators → Add people.
  2. GitHub-Benutzernamen eingeben und einladen.
  3. Die eingeladene Person nimmt die Einladung per E-Mail oder unter github.com/<owner>/<repo>/invitations an.

Collaborators eines persönlichen Repositorys haben Schreibrechte: Sie dürfen klonen, Branches pushen, Pull Requests mergen. Für größere Teams legt man eine Organization an (z. B. für ein Diplomarbeitsteam), in der Rechte feiner vergeben werden können.

ℹ
Ohne Schreibrechte: Fork

Wer kein Collaborator ist — typisch bei Open-Source-Projekten — arbeitet mit einem Fork, einer eigenen Kopie des Repositorys (Abschnitt 8).

2 — Einen Pull Request erstellen

Ausgangspunkt ist ein gepushter Feature-Branch (Lektion 2.1):

Terminal Bash 
git switch -c feature/projekte
git commit -am "Abschnitt Projekte ergänzt"
git push -u origin feature/projekte
# remote: Create a pull request for 'feature/projekte' on GitHub by visiting:
# remote:      https://github.com/maxmuster/steckbrief/pull/new/feature/projekte

Auf GitHub erscheint danach ein gelber Hinweis mit dem Button Compare & pull request. Alternativ: Reiter Pull requests → New pull request. Wichtig ist die Richtung:

FeldBedeutungBeispiel
baseZiel: hierhin soll gemergt werdenmain
compareQuelle: dein Branch mit den neuen Commitsfeature/projekte
Titlekurz, wie eine gute Commit-MessageAbschnitt „Projekte“ mit drei Schulprojekten
DescriptionWas, warum, wie testen? (Markdown)siehe unten
Reviewerswer den Code prüfen sollTeammitglied
Assignees, Labelswer verantwortlich ist, Kategoriedu, „enhancement“

Beschreibungen und Kommentare auf GitHub sind in Markdown geschrieben: ## für Überschriften, - für Listen, - [ ] für Checkboxen, `code` für Code, **fett**. Ein gutes Muster:

Pull-Request-Beschreibung (Markdown) Text 
## Was wurde geändert?
- Neuer Abschnitt „Projekte“ mit drei Karten
- Styling für die Karten in style.css

## Warum?
Die Startseite soll zeigen, woran ich in der Schule gearbeitet habe.

## Wie testen?
1. index.html im Browser öffnen
2. Auf Handybreite prüfen: Karten stehen untereinander

Closes #3

Closes #3 verknüpft den PR mit Issue Nummer 3 (Abschnitt 7). Mit Create pull request wird der PR geöffnet. Wer noch nicht fertig ist, aber schon Feedback möchte, wählt im Pfeilmenü Create draft pull request: Ein Draft kann nicht gemergt werden, bis er mit Ready for review freigegeben wird.

3 — Die Seite eines Pull Requests

ReiterInhalt
ConversationBeschreibung, Kommentare, Reviews, Zeitleiste aller Ereignisse; unten Status der Checks und der Merge-Button
Commitsalle Commits des Branches, die noch nicht in base sind
ChecksErgebnisse automatischer Prüfungen (Lektion 2.5)
Files changedder gesamte Diff gegenüber base — hier findet das Review statt

Ein PR ist an den Branch gebunden, nicht an einzelne Commits: Jeder weitere Push auf feature/projekte erscheint automatisch im offenen PR. Änderungswünsche setzt du also einfach mit neuen Commits auf demselben Branch um — kein neuer PR nötig.

4 — Code Review

Im Reiter Files changed prüft die Reviewerin den Code:

  • Mit dem + neben einer Zeilennummer (oder durch Ziehen über mehrere Zeilen) schreibt sie einen Kommentar zu genau dieser Stelle.
  • Add single comment veröffentlicht sofort; Start a review sammelt mehrere Kommentare und schickt sie gemeinsam ab.
  • Mit dem Symbol Add a suggestion (Plus-Minus-Zeichen) schlägt sie eine konkrete Änderung vor. Der Autor übernimmt sie per Klick auf Commit suggestion — GitHub erstellt dafür einen Commit auf dem Branch.
  • Das Häkchen Viewed klappt fertig geprüfte Dateien zu.
Kommentar mit Änderungsvorschlag (Markdown) Text 
Das alt-Attribut sollte beschreiben, was auf dem Bild zu sehen ist:
```suggestion
  <img src="roboter.jpg" alt="Selbstgebauter Roboter beim Schulwettbewerb">
```

Abgeschlossen wird das Review oben rechts mit Review changes (bzw. Submit review):

ErgebnisBedeutung
CommentFeedback ohne Entscheidung
ApproveZustimmung — aus Sicht der Reviewerin kann gemergt werden
Request changesÄnderungen nötig, bevor gemergt werden darf

Der Autor beantwortet Kommentare, pusht Korrekturen und markiert erledigte Diskussionen mit Resolve conversation. Danach fordert er mit dem Pfeilsymbol neben dem Namen der Reviewerin ein erneutes Review an.

Gutes Review

  • Freundlich und sachlich, über den Code, nicht über die Person
  • Begründen: „… weil Screenreader sonst nichts vorlesen“
  • Fragen stellen statt befehlen: „Was hältst du von …?“
  • Auch Gelungenes erwähnen

Schlechtes Review

  • „Das ist falsch.“ ohne Erklärung
  • Approve, ohne den Code gelesen zu haben
  • Streit über Geschmacksfragen, die ein Formatierungstool regeln könnte
  • Riesige PRs mit 2000 Zeilen anfordern — oder liefern

5 — Konflikte im Pull Request

Wurde in der Zwischenzeit etwas nach main gemergt, das mit deinem Branch kollidiert, zeigt GitHub This branch has conflicts that must be resolved, und der Merge-Button ist gesperrt. Du löst den Konflikt genau wie in Lektion 2.3 — auf deinem Branch:

Terminal Bash 
git switch main
git pull
git switch feature/projekte
git merge main            # Konflikt lösen, git add, git commit
git push                  # der PR aktualisiert sich, der Konflikt ist weg

Für kleine Konflikte bietet GitHub auch den Button Resolve conflicts mit einem Editor im Browser. Gibt es keinen Konflikt, aber main ist weiter, holt Update branch den neuen Stand per Merge (oder im Pfeilmenü per Rebase) in deinen Branch.

6 — Mergen: drei Varianten

Sind Reviews und Checks in Ordnung, wird der PR über den grünen Button gemergt. Das Pfeilmenü daneben bietet drei Varianten:

VarianteErgebnis in mainGeeignet für
Create a merge commitAlle Commits des Branches plus ein Merge-Commit „Merge pull request #7 from …“ (wie git merge --no-ff)Branches mit sauberen, einzeln wertvollen Commits; vollständige Historie
Squash and mergeAlle Commits des Branches werden zu einem neuen Commit zusammengefasstBranches mit vielen kleinen „WIP“/„fix typo“-Commits; ein Commit pro Feature in main
Rebase and mergeDie Commits werden einzeln auf main neu erzeugt, kein Merge-Commit (wie Lektion 2.2)lineare Historie mit allen Einzelcommits

Welche Varianten erlaubt sind, legt der Repository-Owner unter Settings → General → Pull Requests fest. Dort lässt sich auch Automatically delete head branches aktivieren.

Nach dem Merge aufräumen

Terminal Bash 
git switch main
git pull                     # der Merge ist am Server passiert – jetzt lokal holen
git branch -d feature/projekte
git fetch --prune            # gelöschte Server-Branches auch aus origin/… entfernen
⚠
Nach Squash oder Rebase: -d verweigert

Bei Squash and merge und Rebase and merge landen in main neue Commits; deine ursprünglichen Commits kommen dort nicht vor. git branch -d meldet deshalb not fully merged. Wenn der PR auf GitHub als Merged angezeigt wird, ist git branch -D gefahrlos. Arbeite danach nicht auf dem alten Branch weiter, sondern beginne einen neuen von main.

7 — Issues und Pull Requests verknüpfen

Issues (Reiter Issues) sind die Aufgabenliste eines Repositorys: Fehler, Wünsche, Fragen. Jedes Issue hat eine Nummer, z. B. #3, kann Personen zugewiesen und mit Labels versehen werden. Erwähnungen wie #3 in Commits, Kommentaren oder PRs werden automatisch zu Links.

Steht in der PR-Beschreibung eines der Schlüsselwörter Closes, Fixes oder Resolves vor der Nummer, wird das Issue beim Merge in den Standard-Branch automatisch geschlossen:

PR-Beschreibung Text 
Fixes #12
Closes #14
💡
Projektplanung

Mit Projects (Reiter im Repository oder Profil) ordnest du Issues und PRs auf einem Kanban-Board (z. B. „Todo / In Progress / Done“) — nützlich für Gruppen- und Diplomarbeiten.

8 — main schützen: Branch-Regeln

Im Feature-Branch-Workflow soll niemand direkt auf main pushen. Das lässt sich erzwingen: Settings → Rules → Rulesets → New ruleset → New branch ruleset (ältere Variante: Settings → Branches → Add branch protection rule).

EinstellungWirkung
Target branches: Include default branchRegeln gelten für main
Enforcement status: ActiveRegeln werden durchgesetzt
Restrict deletionsmain kann nicht gelöscht werden
Block force pusheskein --force auf main
Require a pull request before mergingÄnderungen nur über PRs; direkte Pushes werden abgelehnt
   Required approvals: 1mindestens eine Zustimmung nötig
Require status checks to passMerge erst, wenn die automatischen Prüfungen grün sind (Lektion 2.5)

Ein direkter Push auf main wird danach vom Server abgelehnt (GH013: Repository rule violations found).

ℹ
Öffentlich oder privat

In öffentlichen Repositories sind diese Regeln kostenlos. Für private Repositories braucht man einen kostenpflichtigen Plan — oder GitHub Pro aus dem Student Developer Pack (Lektion 1.2).

9 — Forks: Beitragen ohne Schreibrechte

Um zu einem fremden Projekt beizutragen, z. B. einen Fehler in einer Open-Source-Bibliothek zu beheben:

  1. Auf der Projektseite Fork klicken — GitHub legt eine Kopie unter deinem Account an.
  2. Deinen Fork klonen, einen Branch anlegen, committen, in deinen Fork pushen.
  3. Auf GitHub einen PR öffnen: base repository = Originalprojekt, head repository = dein Fork.
  4. Die Maintainer des Originals reviewen und mergen — oder auch nicht.
Terminal – Fork aktuell halten Bash 
git remote add upstream https://github.com/original/projekt.git
git fetch upstream
git switch main
git merge upstream/main
git push                       # Fork auf GitHub aktualisieren

upstream ist ein zweites Remote neben origin (deinem Fork). Einfacher geht es auf GitHub mit dem Button Sync fork.

10 — Pull Requests im Terminal: GitHub CLI

Die GitHub CLI (gh, Lektion 1.2) erledigt fast alles ohne Browser:

BefehlWirkung
gh pr create --fillPR für den aktuellen Branch erstellen, Titel/Beschreibung aus den Commits
gh pr listoffene PRs anzeigen
gh pr checkout 7den Branch von PR #7 lokal auschecken, um ihn zu testen
gh pr view 7 --webPR #7 im Browser öffnen
gh pr review 7 --approvePR #7 genehmigen
gh pr merge 7 --squash --delete-branchPR #7 per Squash mergen und den Branch löschen
gh issue create, gh issue listIssues anlegen und anzeigen

Projektschritt

Projektschritt 2.4

Pull Request mit Partner-Review

Arbeite mit einer Partnerin oder einem Partner. Jeder führt die Schritte im eigenen Repository aus und ist Reviewer im anderen.

  1. Lade dein Gegenüber als Collaborator ein.
  2. Lege ein Ruleset für main an: Require a pull request mit 1 Approval, Block force pushes. Teste: Ein direkter Push auf main wird abgelehnt.
  3. Lege ein Issue „Abschnitt Projekte ergänzen“ an.
  4. Erstelle feature/projekte, ergänze den Abschnitt, pushe und öffne einen PR mit Beschreibung nach dem Muster aus Abschnitt 2 und Closes #….
  5. Dein Gegenüber reviewt: mindestens ein Kommentar und ein suggestion, Ergebnis „Request changes“.
  6. Übernimm den Vorschlag (Commit suggestion), setze den Kommentar mit einem eigenen Commit um, fordere ein neues Review an.
  7. Nach dem Approve: Squash and merge, Branch löschen, lokal aufräumen. Prüfe, dass das Issue geschlossen ist.
index.html – Ausschnitt HTML 
<h2>Projekte</h2>
<ul class="projekte">
  <li><strong>Wetterstation</strong> – Arduino, 2. Klasse</li>
  <li><strong>Vokabeltrainer</strong> – Java, 3. Klasse</li>
</ul>
Terminal – nach dem Merge Bash 
git switch main
git pull
git branch -D feature/projekte   # -D, weil per Squash gemergt
git fetch --prune
git log --oneline -3

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: base und compare vertauscht

Der PR zeigt There isn't anything to compare oder will main in den Feature-Branch mergen.

base = Ziel (main), compare = dein Branch. Die Pfeilrichtung im Formular lautet base: main ← compare: feature/….

Fehler: Für jede Korrektur ein neuer Pull Request

Nach dem Review wird ein Branch feature/projekte-2 mit neuem PR angelegt. Die Diskussion des ersten PRs geht verloren.

Korrekturen einfach auf denselben Branch committen und pushen — der offene PR aktualisiert sich automatisch.

Fehler: Nach dem Squash-Merge auf dem alten Branch weiterarbeiten

Auf feature/projekte werden nach dem Merge weitere Commits gemacht und ein neuer PR geöffnet. Er enthält plötzlich wieder alle alten Commits und Konflikte.

Nach dem Merge: git switch main, git pull, alten Branch löschen und für neue Arbeit einen neuen Branch von main anlegen.

Aufgaben

3 Aufgaben + Bonus · zum Aufklappen klicken
Aufgabe 1 Merge-Varianten vergleichen

Erstelle in deinem Repository drei kleine PRs mit je drei Commits und merge sie mit jeweils einer anderen Variante. Vergleiche danach git log --oneline --graph und beschreibe, woran man jede Variante in der Historie erkennt.

Aufgabe 2 Review-Kommentare formulieren

Formuliere die folgenden Rückmeldungen als konstruktive Review-Kommentare um: (a) „Falsch eingerückt.“ (b) „Das Bild hat kein alt.“ (c) „Wozu ist diese Funktion?“ (d) „Passt.“ Begründe jeweils, was den neuen Kommentar besser macht.

Aufgabe 3 PR-Vorlage

Lege in deinem Repository die Datei .github/pull_request_template.md mit den Abschnitten „Was“, „Warum“, „Wie testen“ und einer Checkliste (- [ ] Im Browser getestet, - [ ] Auf Handybreite geprüft) an. Öffne einen neuen PR und prüfe, dass die Vorlage automatisch erscheint.

Bonus Erster Open-Source-Beitrag

Viele Projekte markieren einsteigerfreundliche Issues mit dem Label „good first issue“. Suche auf GitHub ein solches Issue (z. B. in einer Dokumentation), forke das Projekt und bereite einen PR vor. Lies vorher die Datei CONTRIBUTING.md des Projekts. Du musst den PR nicht abschicken — beschreibe aber, welche Schritte du gemacht hast.

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Du willst feature/login in main bringen. Wie stellst du den PR ein?

Erklärung: base ist das Ziel des Merges, compare die Quelle mit den neuen Commits.

Frage 2 Die Reviewerin wünscht Änderungen. Wie setzt du sie um?

Erklärung: Ein PR bezieht sich auf einen Branch. Neue Commits auf diesem Branch erscheinen sofort im PR, die Diskussion bleibt erhalten.

Frage 3 Was bewirkt Squash and merge?

Erklärung: Squash fasst alle Änderungen des PRs zu einem Commit zusammen. Die Einzelcommits des Branches erscheinen nicht in main.

Frage 4 Welche Einstellungen in einem Ruleset verhindern, dass ungeprüfter Code nach main kommt?

Mehrere Antworten sind richtig.

Erklärung: PR-Pflicht, Mindestanzahl an Approvals und grüne Checks sichern die Qualität. Das automatische Löschen von Branches ist nur Aufräumen.

Frage 5 Was passiert, wenn in der Beschreibung eines PRs Fixes #12 steht?

Erklärung: Schlüsselwörter wie Closes, Fixes oder Resolves verknüpfen PR und Issue; beim Merge schließt GitHub das Issue automatisch.

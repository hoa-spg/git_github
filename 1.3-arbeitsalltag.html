Lektion 1.3 — Teil 1: Git-Grundlagen & Werkzeuge

Der Arbeitsalltag mit Git

Arbeitsablauf ca. 90 min Grundlagen

Lernziele

  • Die Zustände einer Datei (untracked, unverändert, geändert, vorgemerkt) erkennen
  • Änderungen mit git diff vor dem Commit überprüfen
  • Kleine, zusammenhängende Commits mit aussagekräftigen Messages erstellen
  • Die Historie mit git log und git show untersuchen
  • Mit einer .gitignore-Datei festlegen, was nicht ins Repository gehört
  • Änderungen auf der passenden Ebene rückgängig machen

1 — Der Kreislauf: ändern, prüfen, vormerken, committen

Aus Sicht von Git befindet sich jede Datei in deinem Arbeitsverzeichnis in einem von vier Zuständen:

ZustandBedeutungAnzeige in git statusWeiter mit
untrackedNeue Datei, Git verfolgt sie nichtUntracked filesgit add
unverändertWie im letzten Commit(nicht angezeigt)bearbeiten
geändert (modified)Bearbeitet, aber nicht vorgemerktChanges not staged for commitgit add
vorgemerkt (staged)Kommt in den nächsten CommitChanges to be committedgit commit

Nach dem Commit sind alle vorgemerkten Dateien wieder „unverändert“ — der Kreislauf beginnt von vorne. Ein typischer Ablauf:

Terminal Bash 
git status                  # Wo stehe ich?
git diff                    # Was genau habe ich geändert?
git add index.html          # Änderung vormerken
git status                  # Ist das Richtige vorgemerkt?
git commit -m "Hobbys ergänzt"
💡
Kurzform von git status

git status -s zeigt eine Zeile pro Datei: ?? = untracked, M = geändert, M = vorgemerkt, A = neu vorgemerkt. Die linke Spalte ist die Staging Area, die rechte das Arbeitsverzeichnis.

2 — Änderungen ansehen mit git diff

Bevor du committest, solltest du wissen, was du committest. git diff zeigt die Unterschiede zeilenweise:

Terminal Bash 
git diff
# diff --git a/index.html b/index.html
# --- a/index.html
# +++ b/index.html
# @@ -8,5 +8,6 @@
#  <body>
#    <h1>Max Muster</h1>
# -  <p>Schüler an der HTL.</p>
# +  <p>Schüler an der HTL, Klasse 3AHIF.</p>
# +  <p>Hobbys: Klettern, Gitarre</p>
#  </body>

Zeilen mit - wurden entfernt, Zeilen mit + hinzugefügt, Zeilen ohne Zeichen dienen als Kontext. Eine geänderte Zeile erscheint als „alte Zeile entfernt, neue Zeile hinzugefügt“. @@ -8,5 +8,6 @@ gibt an, wo der Ausschnitt in der alten und neuen Datei liegt.

Befehlvergleicht
git diffArbeitsverzeichnis mit Staging Area (= was noch nicht vorgemerkt ist)
git diff --stagedStaging Area mit letztem Commit (= was in den nächsten Commit kommt)
git diff a1f3c9e e93c0a2zwei beliebige Commits

3 — Vormerken und committen

BefehlWirkung
git add datei.htmleine Datei vormerken
git add css/alle Änderungen in einem Ordner vormerken
git add .alle Änderungen im aktuellen Ordner und darunter vormerken (vorher git status lesen!)
git rm datei.htmlDatei löschen und das Löschen vormerken
git mv alt.html neu.htmlDatei umbenennen und vormerken
git commit -m "…"Vorgemerktes als Commit speichern
git commit -am "…"alle Änderungen an bereits verfolgten Dateien vormerken und committen (neue Dateien nicht!)

Was ist ein guter Commit?

Ein Commit enthält eine logische Änderung: „Navigation ergänzt“, „Tippfehler im Impressum behoben“. Nicht: „Montag“ oder „alles von heute“. Kleine Commits lassen sich leichter verstehen, prüfen und bei Bedarf einzeln rückgängig machen.

Gute Commit-Messages

  • Kontaktformular ergänzt
  • Falsche Telefonnummer im Footer korrigiert
  • Bilder auf WebP umgestellt (Ladezeit halbiert)
  • Fix: Menü auf dem Handy überdeckte Inhalt

Schlechte Commit-Messages

  • update
  • asdf
  • Änderungen
  • jetzt gehts endlich!!!
  • Erste Zeile: kurze Zusammenfassung (bis ca. 50 Zeichen), ohne Punkt am Ende.
  • Bei Bedarf nach einer Leerzeile weitere Zeilen: warum wurde geändert? (Das „Was“ steht im Diff.)
  • Im Team eine Sprache festlegen — in internationalen Projekten Englisch im Imperativ: „Add contact form“.

4 — Die Historie untersuchen

Terminal Bash 
git log --oneline
# 7a91d2e (HEAD -> main, origin/main) Hobbys ergänzt
# b203833 Steckbrief-Seite angelegt
# f437d39 Initial commit

Der neueste Commit steht oben. In Klammern zeigt Git Markierungen: main ist die Hauptlinie, origin/main der zuletzt bekannte Stand am Server, und HEAD zeigt an, welcher Commit gerade in deinem Arbeitsverzeichnis ausgecheckt ist — normalerweise der neueste Commit von main. Dass main und origin/main hier auf demselben Commit stehen, heißt: Alles ist gepusht.

Befehlzeigt
git logausführliche Liste mit vollem Hash, Autor, Datum, Message (beenden mit q)
git log --oneline -5die letzten 5 Commits, je eine Zeile
git log -p index.htmlalle Commits, die index.html geändert haben, samt Diff
git log --author="Max"nur Commits eines Autors
git show 7a91d2eeinen einzelnen Commit mit seinem Diff
git blame index.htmlfür jede Zeile: in welchem Commit und von wem sie zuletzt geändert wurde
ℹ
Die Historie auf GitHub

Auf GitHub siehst du dieselbe Historie unter Commits (Uhrsymbol über der Dateiliste). Ein Klick auf einen Commit zeigt seinen Diff — rot entfernte, grün hinzugefügte Zeilen.

5 — .gitignore: was nicht ins Repository gehört

Manche Dateien liegen im Projektordner, sollen aber nie committet werden:

ArtBeispieleWarum nicht?
Abhängigkeitennode_modules/riesig, mit npm install wiederherstellbar
Build-Ergebnissedist/, build/, target/, *.classwerden aus dem Quellcode erzeugt
Geheimnisse.env, SchlüsseldateienPasswörter und API-Keys gehören nie in ein Repository
Editor-/IDE-Dateien.idea/, .vscode/, *.imlpersönliche Einstellungen
Betriebssystem-Dateien.DS_Store, Thumbs.dbautomatisch angelegter Müll
Logs, temporäre Dateien*.log, *.tmpändern sich ständig, ohne Wert

Diese Muster schreibst du in eine Datei namens .gitignore im Hauptordner des Repositorys. Die Datei selbst wird committet, damit sie für das ganze Team gilt:

.gitignore Text 
# Abhängigkeiten und Build
node_modules/
dist/

# Geheimnisse
.env
.env.*
!.env.example

# Editor und Betriebssystem
.idea/
.vscode/
.DS_Store
Thumbs.db
*.log
Musterpasst auf
*.logalle Dateien mit Endung .log, in jedem Ordner
dist/Ordner dist mit gesamtem Inhalt
/todo.txtnur todo.txt im Hauptordner (führender Schrägstrich)
!.env.exampleAusnahme: diese Datei doch verfolgen
# …Kommentar
💡
Vorlagen

Für fast jede Sprache gibt es fertige Vorlagen unter github.com/github/gitignore (z. B. Node.gitignore, Java.gitignore). GitHub bietet sie auch beim Anlegen eines Repositorys an. Projektgeneratoren wie Vite oder Angular CLI legen die passende .gitignore selbst an.

⚠
.gitignore wirkt nur auf noch nicht verfolgte Dateien

Wurde eine Datei bereits committet, ignoriert Git sie auch nach dem Eintrag in .gitignore nicht. Du musst sie zuerst aus dem Repository entfernen (die Datei auf der Festplatte bleibt erhalten):

Terminal Bash 
git rm --cached -r .idea
git commit -m ".idea nicht mehr versionieren"

6 — Änderungen rückgängig machen

Was du tun musst, hängt davon ab, wie weit die Änderung schon gekommen ist:

SituationBefehlWirkung
Datei geändert, nicht vorgemerkt — Änderung verwerfengit restore index.htmlDatei wieder wie im letzten Commit. Die Änderung ist weg!
Versehentlich vorgemerktgit restore --staged index.htmlaus der Staging Area nehmen, Änderung bleibt in der Datei
Letzter Commit: Tippfehler in der Message oder Datei vergessen — noch nicht gepushtgit add vergessen.css
git commit --amend -m "…"		ersetzt den letzten Commit durch einen korrigierten (neuer Hash)
Ein Commit war falsch — bereits gepushtgit revert 7a91d2eerzeugt einen neuen Commit, der die Änderungen von 7a91d2e umkehrt; die Historie bleibt erhalten
Eine alte Version einer Datei zurückholengit restore --source=b203833 index.htmlDatei im Arbeitsverzeichnis auf den Stand dieses Commits setzen, danach normal committen
✗
Gepushte Commits nie umschreiben
--amend (und andere Befehle, die Commits ersetzen) ändern die Hashes. Wurden die Commits schon gepusht und haben andere sie geholt, passt ihre Historie nicht mehr zur Historie am Server. Für gepushte Commits deshalb immer git revert verwenden.
⚠
git reset --hard

Im Internet liest du oft git reset --hard. Der Befehl verwirft alle nicht committeten Änderungen und kann Commits „verschwinden“ lassen. Verwende ihn erst, wenn du genau weißt, was er tut.

Projektschritt

Projektschritt 1.3

Saubere Commits und eine .gitignore

  1. Lege im Repository steckbrief eine .gitignore an und committe sie allein:
steckbrief/.gitignore Text 
.DS_Store
Thumbs.db
.idea/
.vscode/
*.log
  1. Lege style.css an und binde sie in index.html ein (<link rel="stylesheet" href="style.css"> im <head>). Committe beide Dateien gemeinsam — sie gehören zu einer logischen Änderung.
  2. Ergänze in index.html einen Absatz mit deinen Hobbys. Prüfe vor dem Commit mit git diff, dann eigener Commit.
  3. Pushe und kontrolliere die Historie lokal und auf GitHub:
Terminal Bash 
git add .gitignore
git commit -m ".gitignore angelegt"
git add style.css index.html
git commit -m "Stylesheet eingebunden"
git diff
git commit -am "Hobbys ergänzt"
git push
git log --oneline

Ergebnis: drei neue, klar beschriebene Commits auf GitHub.

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: Neue Datei mit commit -am vergessen

Nach git commit -am "Galerie ergänzt" fehlt galerie.html im Commit — die Datei war neu (untracked).

-a erfasst nur bereits verfolgte Dateien. Neue Dateien immer mit git add vormerken und vor dem Commit git status lesen.

Fehler: Passwort committet und „wieder gelöscht“

Die Datei .env mit einem API-Key wurde gepusht, im nächsten Commit gelöscht. Der Key ist trotzdem in der Historie und auf GitHub für jeden lesbar.

Geheimnisse sofort beim Anbieter ungültig machen und neu erzeugen. Vorbeugend .env von Anfang an in .gitignore eintragen.

Fehler: Ein Riesen-Commit am Ende des Tages

Ein einziger Commit „Änderungen“ enthält Layout, Texte, einen Bugfix und eine halbfertige Funktion. Der Bugfix lässt sich nicht einzeln übernehmen oder rückgängig machen.

Nach jedem abgeschlossenen Arbeitsschritt committen; zusammengehörige Dateien gezielt mit git add <datei> vormerken.

Aufgaben

3 Aufgaben + Bonus · zum Aufklappen klicken
Aufgabe 1 Zustände beobachten

Lege in einem Übungsrepository eine neue Datei an, ändere eine bestehende und lösche eine dritte (mit git rm). Führe nach jedem Schritt git status und git status -s aus und notiere, in welchem Zustand jede Datei ist. Merke dann nur zwei der drei Änderungen vor und committe.

Aufgabe 2 Commit-Messages verbessern

Schreibe für folgende Änderungen je eine gute Commit-Message: (a) Die Schriftgröße auf dem Handy war zu klein. (b) Die Seite „Über uns“ ist neu. (c) Ein Link im Footer zeigte auf eine nicht existierende Seite. (d) node_modules wurde versehentlich committet und wird entfernt.

Aufgabe 3 Rückgängig machen üben

Spiele jede Zeile der Tabelle in Abschnitt 6 in deinem Übungsrepository durch. Kontrolliere jeweils mit git status und git log --oneline, was passiert ist. Bei welchen Befehlen ändert sich die Commit-Historie, bei welchen nicht?

Bonus Detektivarbeit

Klone ein großes Open-Source-Repository (z. B. https://github.com/expressjs/express). Finde mit git log heraus: Wann war der erste Commit? Wer hat die meisten Commits (Tipp: git shortlog -sn | head)? Wer hat zuletzt die Datei Readme.md geändert?

Quiz

5 Fragen · zum Aufklappen klicken

Frage 1 Was zeigt git diff --staged?

Erklärung: --staged vergleicht die Staging Area mit dem letzten Commit. Ohne Option zeigt git diff die noch nicht vorgemerkten Änderungen.

Frage 2 Welche Dateien gehören typischerweise in die .gitignore?

Mehrere Antworten sind richtig.

Erklärung: Abhängigkeiten, Geheimnisse und automatisch erzeugte Systemdateien gehören nicht ins Repository. Quellcode wie index.html natürlich schon.

Frage 3 Ein bereits gepushter Commit hat einen Fehler eingebaut. Wie machst du ihn sicher rückgängig?

Erklärung: git revert erzeugt einen neuen Commit, der die Änderung umkehrt, ohne die bestehende Historie zu verändern. --amend schreibt den letzten Commit um und ist nur für ungepushte Commits geeignet.

Frage 4 Du hast config.json committet und erst danach in .gitignore eingetragen. Was passiert?

Erklärung: .gitignore betrifft nur Dateien, die Git noch nicht verfolgt. Bereits verfolgte Dateien muss man mit git rm --cached aus dem Repository nehmen.

Frage 5 git log --oneline zeigt 7a91d2e (HEAD -> main, origin/main) Hobbys ergänzt. Was folgt daraus?

Erklärung: origin/main ist der zuletzt bekannte Stand von main am Server. Steht er beim selben Commit wie das lokale main, ist alles gepusht. HEAD markiert den ausgecheckten Commit.
